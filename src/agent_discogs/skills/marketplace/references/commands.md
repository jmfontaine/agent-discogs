# Marketplace Command Reference

## Nouns

### `price @r...`

Price suggestions by condition (Mint, Near Mint, VG+, etc.) and marketplace stats, each amount with the ISO currency code Discogs returns: `Mint (M): EUR 20.00`, `Lowest: GBP 9.99`. It needs a token or OAuth *and* seller settings on that account (see Setup in `agent-discogs skills get core`).

### `get stats @r... [@r...]`

The numbers that compare pressings, one line per release (1-10 release refs or raw ids, blocks separated by a blank line): `@r847868 "The Downward Spiral" by Nine Inch Nails 1994 · have 7,618 · want 1,355 · rating 4.43/5 (602 votes) · for sale: 45 from EUR 0.80`. `have`, `want` and the community rating come from the release record (`GET /releases/{id}`); the count for sale and the lowest price come from its Marketplace stats (`GET /marketplace/stats/{id}`), which name the currency: the account's buyer currency (USD without credentials), or `--currency CODE` (`USD`, `GBP`, `EUR`, `CAD`, `AUD`, `JPY`, `CHF`, `MXN`, `BRL`, `NZD`, `SEK`, `ZAR`, any case; sent as `curr_abbr` on the stats request only; another code is `invalid_argument` before any request). A part Discogs did not send is left out (no rating when nobody voted). Nothing for sale, and a release blocked from sale, print `· for sale: 0`; a count with no price prints `· for sale: 3`, with no `from`. **Cost: 2 requests per ref** (20 for 10), the release first, so a release that does not exist costs 1; no username, profile, seller settings or user needed. A ref that is not a release, a 404, a 429 or a `--cached` miss on either request makes that ref its `✗` block (JSON `{"ref","error"}`), never a half line; the others still run and the command exits 1. Takes `--currency` only (besides `--json`, `--full`).

### `get versions @m... --market`

Each version row ends in its Marketplace numbers, after the `--owned`/`--wanted` marks: `@r847868 1994 US · Nothing Records 92346-2 · CD, Album · have 7,544 · want 1,113 · for sale: 45 from EUR 0.80`, `· for sale: 0` (nothing for sale, or blocked from sale: Discogs sends `null` counts for both), `· for sale: 3` (no price). One `GET /marketplace/stats/{id}` per row shown, after the listing and on top of its own cost, cached 1h: **for a server-side page of N rows, 1 + N requests with `--json`, 2 + N as text** (the header's master title is read first), 2 + N in either mode from a release ref (the release lookup); a `--release-type official` (or `unofficial` with `--format`) scan reads its S pages first, **S + N with `--json`, 1 + S + N as text or from a release ref**. `--currency CODE` (any case) goes on every lookup and is accepted on `get versions` only with `--market` (`--currency needs --market with get versions.`); without it each price names the currency Discogs chose (the account's, USD without credentials). No user needed. Free to combine with every `get versions` flag; `Next page:` repeats `--market` and `--currency`.

- **`--max-requests N`** is accepted with `--market` (one ref): the header and the server-side listing page are always sent (a `--release-type` scan reads pages only while the shared cap allows), then a row's lookup only while fewer than N requests were sent; cache hits are free. Rows past the cap are unchecked (no tail; JSON `"market": null`) and a note says so: `Market: the lookups stopped at --max-requests 4 (2 of 5 rows checked): rows without "for sale:" were not checked.` A rerun of the same command reads the checked rows from the cache and spends the cap on the rest.
- **429** on a lookup: the lookups stop, the rows read keep their numbers, exit 0, note `Market: a lookup was rate limited, retry in 30s (2 of 5 rows checked): ...`. A `--release-type` scan stopped by its own 429 sends no lookup (`Market: the listing was rate limited, ...`). Any other lookup failure (5xx, a removed release's 404) fails the command; a 429 on the first page is the usual `rate_limited` error.
- **`--cached`**: a row whose stats are not cached ends `· ✗ Not cached: GET /marketplace/stats/847868` and the command exits 1 after `Rerun without --cached to check the rows marked ✗.`; as text the header must be cached too.

### `get wantlist`

Your own wantlist, 5 wants a page (`--limit` 1-100, `--page`), no ref (a ref is `invalid_argument`): header `Wantlist: me (page 1, 5 of 150 wants)`, rows like `@r847868 "Nine Inch Nails - The Downward Spiral" 1994 · Nothing Records 92346-2 · CD (Album) · notes: Sealed only` (the title is just the artist when Discogs sent no title), then `Next page: ...`. JSON rows carry `ref`, `title`, `year`, `label`, `catno`, `format`, and `notes`/`rating` when set (`rating` 0 = unrated is omitted; `--json --full` is the SDK's want records: `id`, `basic_information`, `notes`, `rating`, `resource_url`). Needs a token or OAuth, like `--owned` (`auth_required` before any request otherwise). Cost: 1 for the username (cached an hour) + 1 per page of up to 100 wants. Copy a row's `@r...` into `get release`, `price` or `get owned`. Only your own wantlist: no `--user`, and nothing adds or removes wants.

### `get wantlist --for-sale [--max-price X --currency EUR]`

Only the wants with copies for sale now, each row ending `· for sale: 3 from EUR 12.50` (JSON `market`: `{"for_sale":3,"lowest":12.5,"currency":"EUR"}`, `lowest`/`currency` omitted when Discogs gives no price). Kept = at least one copy for sale and not blocked from sale; with `--max-price X` also lowest price at most `X` (exactly `X` is kept, no price is dropped). `--currency` is one of USD GBP EUR CAD AUD JPY CHF MXN BRL NZD SEK ZAR (any case) and prices every stats request; without it each price is in the account's buyer currency and names it. `--max-price` requires `--currency`: the threshold is a bare number, so you name its currency rather than have the account's assumed. `--limit` is how many for-sale wants to collect (default 5). **It costs 1 request per want checked** (each want's Marketplace stats, cached an hour; wants are read 100 per request) and has no default cap: a 500-want list with few matches is ~500 requests, ~9 minutes of the 60/min budget. **Always pass `--max-requests N`** (60 is one minute): it counts every send, is checked before each want, and ends in `Continue scan: agent-discogs get wantlist --for-sale --max-requests N --after P:R` (JSON `capped: true`, `stop_reason: "max_requests"`, `next_cursor`), where the cursor names the first want not yet checked, so pasting it never re-checks one. A 429 on any stats request keeps the rows matched so far (`stop_reason: "rate_limited"`, `retry_after`) with a `Continue scan:` from that want; a want whose stats were not read is never reported as not for sale. `--page` is rejected with `--for-sale` (use the continuation), and `--max-price`, `--currency`, `--max-requests` and `--after` need `--for-sale`. `--fresh` when current Marketplace numbers matter (stats are cached an hour). Under `--cached`, a want whose stats are not cached is a row ending `· ✗ Not cached: GET /marketplace/stats/5` (JSON row `error.code: "cache_miss"`), counts toward `--limit`, and the command exits 1: rerun those wants without `--cached`.

### `get inventory <username>`

One seller's Marketplace listings (`GET /users/{username}/inventory`), 5 a page (`--limit` 1-100, `--page`), with the username where other nouns take a ref (exactly one; a name starting with `-` goes after `--`): header `Inventory: redscroll (page 1, 5 of 300 listings)` (filters appear in it: `condition≥NM sleeve≥G ships-from=France max-price=45.5 currency=EUR`, each grade as the minimum it is, `in wantlist` after the username), rows like `@r847868 "Nine Inch Nails - The Downward Spiral" · CD, Album · NM/VG+ · USD 12.50 · ships from Germany · listed 2024-09-18` (release ref, format, media/sleeve grade as short codes (a sleeve that is no grade, such as Generic, Not Graded or No Cover, prints as sent; no sleeve sent gives the media code alone; no media grade but a sleeve reads `?/VG+`), price with its ISO code, ships-from country, the day listed in US Pacific time (as Discogs sends it, not the seller's); whatever Discogs did not send is left out, and a listing with no release id starts `listing <id>`), then `Next page: ...`. It works without credentials: Discogs shows anyone a seller's For Sale listings, and shows non-owners only those. `--sort listed|price|item|artist|label|catno` and `--desc` go to Discogs. **Filters** keep the matching listings, and any of them makes it a client-side scan (`≤N` totals, `--after`, `--max-requests`, no `--page`): `--condition GRADE` and `--sleeve GRADE` (minimum grade, M > NM > VG+ > VG > G+ > G > F > P, as the code or the full name such as `Very Good Plus (VG+)`, any case; a Generic, Not Graded or No Cover sleeve fails any `--sleeve`), `--ships-from COUNTRY` (exact, any case), `--max-price X --currency EUR` (listings priced in that currency up to X, each flag needing the other; here `--currency` is matched against each listing's currency and never sent to Discogs, unlike on `get wantlist --for-sale`; a listing in another currency is dropped and counted, `N listings in other currencies skipped`, JSON `pagination.skipped_currency`; sellers price in their own currency, so pick theirs), and `--in-wantlist` (listings whose release is on your wantlist; needs a token or OAuth; it reads your whole wantlist first, 1 request for the username + 1 per 100 wants, and when `--max-requests` or a 429 stops that read no listing is scanned: an empty capped page with `Continue scan:`, JSON `wantlist.complete: false`). `--owned` marks rows by the listing's release id. **Cost: 1 request per page; with a filter 1 per 100 listings scanned (a seller with 50,000 listings is 500 requests), so always pass `--max-requests` with a filter.** Cached an hour. JSON rows: `listing` (the listing id), `ref` (the release), `title`, `format`, `condition`, `sleeve`, `price`, `currency`, `ships_from`, `listed` (RFC 3339), `url` (`https://www.discogs.com/sell/item/<id>`); `--json --full` is the SDK's listing records (`id`, `condition`, `sleeve_condition`, `price`, `original_price`, `shipping_price`, `ships_from`, `posted`, `release`, `seller`, ...).

### `--wanted`

`--wanted` (on `search`, `get versions`, `get releases @a...|@l...`) marks each *release* row with your wantlist: `· wanted`, `· not wanted`, or `· wanted ?` (undecided), after the `--owned` mark when both are given (`· owned · wanted`). JSON rows get `wanted`: `true`, `false` or `null`, always present on a release row; master, artist and label rows get none. Needs a token or OAuth (`--wanted reads your own Discogs account, but no credentials are set.`, `auth_required` before any request). **`get versions` and `get releases`** rows carry your own want count (`stats.user.in_wantlist`; 1 or more is wanted), so nothing more is sent and there is no `wantlist` object; a row without it is `wanted ?`. `--wanted` there leaves nothing to cap, as `--owned` does: `--max-requests` needs a client-side scan (`get versions --release-type official`, or `unofficial` with `--format`; `get releases --role`; a label's `--year`) or the `get versions --market` lookups (capped together with the scan), and is otherwise `invalid_argument` before any request. **`search`** reads your whole wantlist once after the listing page (1 request for the username, shared with `--owned`, then 1 per 100 wants; cached an hour) and adds a `wantlist` object `{"complete","wants_read","total_wants"}` (plus `stop_reason`/`retry_after`). `--max-requests N` caps that read too: with nothing left after the listing (and the `--owned` read), not even the username is asked. A read cut short by the cap or a 429 never claims a release is not wanted: a want found in the part read is `wanted`, every other row `wanted ?`, with a note `Wantlist: the read stopped at --max-requests 3 (100 of 250 wants read): "wanted ?" rows are not in the part read.` before the footer; after a listing scan or collection read that stopped on a 429, the wantlist is not read at all. Rejected before any request: `search artist|label|master ... --wanted`, `--wanted --added-since`, and `--wanted` on any other `get` noun (`get inventory` points at `--in-wantlist`). Under `--cached`, `search` fails with `cache_miss` on the username or a wants page not cached. The printed `Next page:` / `Continue scan:` repeats `--wanted`.

## JSON

`get stats --json` is `{"ref","title","artists","year","community":{"have","want","rating","votes"},"market":{"for_sale","lowest","currency"}}` for one ref, a list for several (`{"ref","error"}` items for failures). `rating` is left out when `votes` is 0. `market` is the object `get wantlist --for-sale` rows carry: `for_sale` is `0` when Discogs sends `null` (nothing for sale, or blocked from sale), `lowest`/`currency` are omitted when it gives no price, and a release blocked from sale adds `"blocked": true`. `--json --full` is `{"release": <the release record>, "marketplace_stats": <the stats record>}`.

`get versions --market --json` rows gain `market` (the same object; `null` for a row not checked, and `{"error"}` instead for a `--cached` miss) and the document `market_read`: `{"complete": true, "rows_read": 5, "rows": 5}`, plus `stop_reason` (`"max_requests"` or `"rate_limited"`) and `retry_after` when the lookups stopped short. `--full` adds `market` to the version records the same way, and `market_read` to the document.

`get wantlist --json` is `{"pagination":{...},"results":[{"ref","title","year","label","catno","format","notes","rating"}]}`; with `--for-sale` each kept row adds `market` and `pagination` is the filtered-scan envelope, and under `--cached` a want whose stats are not cached is a row with `error` instead of `market` (exit 1).

`get inventory --json` is `{"pagination":{...},"results":[{"listing","ref","title","format","condition","sleeve","price","currency","ships_from","listed","url"}]}`; with a filter `pagination` is the filtered-scan envelope (plus `skipped_currency` with `--max-price`), with `--in-wantlist` the document has a `wantlist` object `{"complete","wants_read","total_wants"}` (`stop_reason`/`retry_after` when its read stopped, in which case `results` is empty), and with `--owned` rows carry `owned` and the document `collection`.

## `get wantlist --for-sale` scan

A client-side scan over your wantlist (100 wants a page) that asks Discogs for each want's Marketplace stats (`GET /marketplace/stats/{id}`, cached 1h), so it costs 1 request per want checked on top of the username and the wants pages, with no default cap: a 500-want list with few for sale is about 500 requests, roughly 9 minutes of the 60/min budget. Always pass `--max-requests N` (60 is one minute; N must be 3 or more, `invalid_argument` otherwise: the username, a wants page and one want's stats, which a cold cache or `--fresh` sends on every run). The cap counts every send of the command (username, wants pages, stats) and is checked before each want, so the scan can stop mid-page; a wants page is asked for only while at least 2 sends remain after the sends so far (the page and one want's stats), so at a page boundary the scan stops with the boundary cursor without reading the next page. It ends in `Continue scan: agent-discogs get wantlist --for-sale --max-requests N --after P:R` (JSON `capped: true`, `stop_reason: "max_requests"`, `next_cursor`), and the cursor names the first want not yet checked, so the continuation never checks one twice. A 429 on any stats request keeps the rows matched so far (`stop_reason: "rate_limited"`, `retry_after`) with a `Continue scan:` from the want it answered; a 429 on the username or the first wants page is the `rate_limited` error. A want whose stats were not read is never reported as not for sale.

## `get inventory` scan

With any of `--condition`, `--sleeve`, `--ships-from`, `--max-price` or `--in-wantlist`, `get inventory` is a client-side scan over the seller's listings (100 a page): 1 request per 100 listings scanned, with no default cap, so a seller with 50,000 listings is 500 requests (over 8 minutes of the 60/min budget, 20 at the unauthenticated 25/min). Always pass `--max-requests N` (1 or more; 60 is one minute). It counts every send of the command: the `--in-wantlist` username and wants pages, the inventory pages and the `--owned` collection pages. Without a filter `--max-requests` is accepted only with `--owned` (`invalid_argument` otherwise: a plain inventory pages server-side, 1 request per page). `--in-wantlist` first reads your whole wantlist (1 request for the username, then 1 per 100 wants, cached 1h): a listing is kept only against the complete wantlist, so when that read stops short (the cap, or a 429 on the username or a wants page) no listing is scanned and the command prints an empty capped page, exit 0, with the header `Inventory: seller in wantlist (--max-requests 2 ran out before the scan started)` (or `(rate limited before the scan started, retry in 30s)`), a note `Wantlist: the read stopped at --max-requests 2 (100 of 150 wants read), so no listing was scanned: a listing is kept only against the whole wantlist.` and a `Continue scan:` with the cursor asked for; JSON `results: []`, `pagination` with `total_items: null`, `capped: true`, `next_cursor: "1:0"` and `stop_reason`, plus `wantlist` `{"complete":false,"wants_read":100,"total_wants":150,"stop_reason":"max_requests"}`. Pasting the `Continue scan:` with a higher cap works: the wants already read come from the cache for free. A 429 on an inventory page after the first keeps the rows matched so far.

## `--cached`

Under `--cached`, `get wantlist` fails with `cache_miss` on the username or a wants page; under `--for-sale`, a want whose Marketplace stats are not cached becomes a row with its own `cache_miss` error and the command exits 1. `get inventory` fails so on an inventory page, and with `--in-wantlist` also on the username or a wants page; `get inventory` alone sends no username request. `get stats` fails each ref whose release or stats is not cached with `cache_miss`, sending nothing.

## Flags for `get wantlist`

| Flag | Description |
|------|-------------|
| `--for-sale` | Keep only the wants with copies for sale now, each row ending `· for sale: 3 from EUR 12.50` (`· for sale: 3` when Discogs gives no price); JSON rows gain `market`: `{"for_sale":3,"lowest":12.5,"currency":"EUR"}`. A want is kept with at least one copy for sale and not blocked from sale (`blocked_from_sale`). 1 request per want checked: see the `get wantlist --for-sale` scan above, and always pass `--max-requests`. |
| `--max-price` | With `--for-sale`: keep wants whose lowest price is at most this amount (exactly the amount is kept; a want with copies but no lowest price is dropped). Needs `--currency`; a negative amount is `invalid_argument`. |
| `--currency` | With `--for-sale`: `USD`, `GBP`, `EUR`, `CAD`, `AUD`, `JPY`, `CHF`, `MXN`, `BRL`, `NZD`, `SEK` or `ZAR` (any case, sent uppercase; Tab completes it; another code is `invalid_argument` before any request). Prices every stats request in that currency; without it Discogs prices in the account's buyer currency, and each price names it (`USD 12.50`, JSON `market.currency`). |

`--max-price`, `--currency` and `--max-requests` without `--for-sale`, and `--after` without it, fail with `invalid_argument` before any request, as do `--max-price` without `--currency`, an unknown `--currency` code, and `--max-requests` below 3 with `--for-sale` (`--max-requests must be 3 or more with --for-sale (2 given): the username, a wants page and one want's stats, which a cold cache or --fresh sends on every run.`). A for-sale row under `--cached` whose stats are not cached ends `· ✗ Not cached: GET /marketplace/stats/5` (JSON `error.code: "cache_miss"`, no `market`), counts toward `--limit`, and exits 1; the text adds `Rerun without --cached to check the wants marked ✗.`

## Flags for `get inventory`

| Flag | Description |
|------|-------------|
| `--sort` | `listed`, `price`, `item`, `artist`, `label` or `catno` (server-side, over the whole inventory; Tab completes them) |
| `--desc` | With `--sort`: descending |
| `--condition` | Keep listings whose media grade is this or better. Scale: `M` > `NM` > `VG+` > `VG` > `G+` > `G` > `F` > `P` (Mint to Poor). Short code or full Discogs name (`Very Good Plus (VG+)`), any case; anything else is `invalid_argument` before any request (`--condition must be a Discogs grade: M, NM, VG+, VG, G+, G, F or P, or its full name such as 'Very Good Plus (VG+)' (any case; 'mint-' given).`). Tab completes the codes. |
| `--sleeve` | Keep listings whose sleeve grade is this or better; same scale and spelling. A Generic, Not Graded or No Cover sleeve fails any `--sleeve`. |
| `--ships-from` | Keep listings shipping from this country, exact match on the country as Discogs names it, any case (`germany` matches `Germany`, `Germ` does not). Blank is `invalid_argument`. |
| `--max-price` | Keep listings priced in `--currency` at this amount or less (exactly the amount is kept; a listing with no price is dropped). Needs `--currency`; a negative or non-finite amount is `invalid_argument` (a value that is not a number, such as `abc`, is a usage error, exit 2). A listing priced in another currency is dropped and counted: the header says `N listings in other currencies skipped` (`1 listing in another currency skipped`) and JSON `pagination.skipped_currency` is present whenever `--max-price` is given, 0 included; the count covers the listings that passed every other filter, in the part this run scanned. |
| `--currency` | With `--max-price` only (alone it is `invalid_argument`): `USD`, `GBP`, `EUR`, `CAD`, `AUD`, `JPY`, `CHF`, `MXN`, `BRL`, `NZD`, `SEK` or `ZAR` (any case; Tab completes it). Here it is matched client-side against each listing's price currency and never sent to Discogs, unlike `wantlist --for-sale`, where it is sent as `curr_abbr` and prices the stats. Discogs reports a seller's price in the seller's own currency (observed: USD, EUR, GBP), so pick the seller's currency and expect skipped counts for a seller who prices in another. |
| `--in-wantlist` | Keep listings whose release is on your wantlist. Needs a token or OAuth (`auth_required` before any request otherwise). Reads your whole wantlist first (see the `get inventory` scan above); JSON adds a top-level `wantlist` object `{"complete":true,"wants_read":150,"total_wants":150}`. |

Any filter makes `get inventory` a client-side scan: 100-listing pages in the requested order, `--limit` counts matches, `≤N` totals, `--page` rejected, continue with the printed `Continue scan:` / `Next page:` (`--after`, which also repeats the filters, `--sort`, `--desc` and `--in-wantlist`), cap with `--max-requests N`. Without a filter it pages server-side (`--limit` 1-100, `--page`).

## Examples

```bash
agent-discogs get price @r847868
agent-discogs get stats @r847868 @r352665 --currency EUR
agent-discogs get versions @m3719 --format Vinyl --market --currency EUR --limit 20 --max-requests 30
agent-discogs get wantlist
agent-discogs get wantlist --limit 100 --page 2
agent-discogs get wantlist --for-sale --max-price 20 --currency EUR --max-requests 60
agent-discogs get inventory redscroll --sort price --desc --limit 20
agent-discogs get inventory redscroll --condition NM --sleeve VG+ --ships-from Germany --max-requests 20   # client-side scan; continue with the printed --after
agent-discogs get inventory redscroll --max-price 30 --currency USD --max-requests 20
agent-discogs get inventory <seller> --in-wantlist --condition VG+ --max-requests 60   # your wantlist read first, then the scan
```
