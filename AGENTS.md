# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## Project Overview

A token-efficient Discogs CLI designed for AI agents. Built on click and the `discogs-sdk` Python SDK.

## Commands

Task runner is `just`. All commands use `uv run` under the hood.

```bash
just setup                             # Install deps + pre-commit hooks (main checkout only; see below)
just test                              # Run pytest; fails below 100% coverage of src/agent_discogs
just test <path> --cov-fail-under=0    # Run specific test file or directory (a partial run can't reach 100%)
just test-live                         # Run only the `live` tests against the real Discogs API (needs DISCOGS_TOKEN; skipped without it)
just qa                                # All checks: dead-code, deps-unused, format-check, lint, type-check, verify-types
just lint                              # ruff check
just lint-fix                          # ruff check --fix
just format                            # ruff format + pyproject-fmt
just type-check                        # ty check
just dead-code                         # deadcode src tests (via uvx, Python 3.13)
just deps-unused                       # deptry src
just deps-update                       # Update deps to latest versions
just verify-types                      # Audit public API type annotation coverage
just release-prepare [X.Y.Z]           # Open the pull request that sets the release version
just release                           # Tag, push, and monitor the publish workflow (the user only; see Releasing)
just release-next [minor|patch|major]  # Open the pull request that starts the next development version
just pre-commit                        # Run pre-commit hooks on all files
just pre-commit-install                # Install pre-commit hooks (main checkout only)
just pre-commit-update                 # Update pre-commit hooks to latest versions
```

Run a single test: `uv run pytest tests/test_cli_basics.py -k test_version`

### Worktrees

Every linked worktree (`git worktree add`) shares the main checkout's `.git/hooks`. In a linked worktree, never run `just setup`, `just pre-commit-install`, `pre-commit install`, `prek install`, or anything else that writes `.git/hooks` or sets `core.hooksPath`: an installer replaces the hook every checkout uses, moving the existing one to `pre-commit.legacy` to run in pre-commit's "migration mode" (a prek hook there fails every commit), and points the new hook at the worktree's `.venv`, which disappears with the worktree. Get a working environment with `uv sync --all-extras --all-groups` instead. Both recipes check for a linked worktree (`git rev-parse --git-dir` differs from `--git-common-dir`): `just setup` installs the dependencies and skips the hook, `just pre-commit-install` exits 1. The guard does not cover running an installer directly. If a commit hook fails for a reason unrelated to your change, stop and report it; never bypass it with `--no-verify`.

## Architecture

### CLI (click)

Entry point: `src/agent_discogs/__init__.py`. Defines a `click.Group` with `AliasGroup` for command aliases (`find`→`search`, `query`→`search`, `fetch`→`get`, `show`→`get`). Top-level shortcuts `tracks` and `price` delegate to `get` logic. The group callback owns the global flags: `--color` is recorded first (`style.configure()`), `--debug` (also `AGENT_DISCOGS_DEBUG`) starts the trace, `--cached` / `--fresh` record a pending SDK `cache_only()` / `no_cache()` scope with `client.request_cache_scope()`. The callback runs before the subcommand validates its flags, so it never builds the client itself: the first `get_client()` call enters the scope on the root context (`ctx.with_resource()`), and it lasts until the command ends. A rejected flag therefore builds no client. A global flag typed after the subcommand is click's `NoSuchOption`; `AliasGroup.invoke` rewrites it, for the names in `_GLOBAL_OPTIONS` (kept next to the group's options: add a new global flag there too), into one saying to put it before the command, without click's did-you-mean.

### Command Modules

- `commands/search.py` — Search Discogs database. Positional args with optional type prefix (`release`, `master`, `artist`, `label`). `--added-since` (`search release` only) is a thin wrapper around the SDK's experimental `discogs_sdk.experimental.releases_added_since()` (with `per_page=100` and the command's `--max-requests`): it returns the whole window of looked-up `Release` models, filters `--release-type` on their formats (unofficial goes to Discogs as `format=Unofficial Release` unless `--format` is given), and applies `--limit` only when the user passed it (click's parameter source). Its conflicts (`--sort`, `--desc`, `--page`, `--after`, a non-release search) are rejected before any request.
  `--owned` (any search that can return release rows: not `search artist|label|master`, not with `--added-since`) marks each release row with the user's copies through `collection.ownership_of()` after the page is fetched; it is also accepted with `--max-requests`, which then caps the collection read. `--wanted` (same rows, same rejections) marks them through `inventory.wants_of()`, which reads the wantlist after the collection read, sends nothing when the cap is spent or when the listing or collection read already stopped on a 429, and adds the `wantlist` object.
- `commands/get.py` — Get entity details by noun (`artist`, `collection`, `credits`, `identifiers`, `inventory`, `label`, `list`, `lists`, `master`, `owned`, `price`, `release`, `releases`, `stats`, `tracklist`, `versions`, `wantlist`) for one or more refs (`MAX_REFS`). Handlers return text or a JSON document; `_dispatch` collects one block per ref in order and prints them once (text: blank-separated on stdout, a failing ref becomes its `✗` block; JSON: a list with `{"ref", "error"}` items), exiting 1 if any failed. A single ref keeps the single-document shape and the `fail()` error path. Also defines `tracks` and `price` shortcut commands. The `owned` noun (`get owned @r...`, release refs and raw ids) asks `collection.copies()` about one release at a time; it also takes master refs (`NOUN_ALSO_ACCEPTS`, which `_resolve_ref()` accepts and names in its type error), which `_get_owned_master()` answers through `collection.master_copies()`; `--owned` on `releases` and `versions` marks their release rows from each row's own count (`collection.stat_copies()`, Discogs' `stats.user.in_collection`), sending nothing more and printing no `collection` object, so `--max-requests` there still needs a scan (or `versions --market`); on `inventory` it reads the collection through `collection.ownership_of()`. Both call `account.require_user()` before any request. The `collection`, `lists` and `wantlist` nouns take no ref: they are in `REFLESS_NOUNS`, which makes `REF...` optional for `get` (every other noun still raises click's `Missing argument 'REF...'`), and `_get_collection()` / `_get_lists()` / `_get_wantlist()` print one document for the user's own collection, lists or wantlist, after `account.require_user()` and the username. The `list` noun is in `ID_NOUNS`: its refs are bare ids (`_resolve_ref()` rejects anything else, a typed ref included, with `invalid_argument`), and `_get_list()` reads one list (`client.lists.get()`, every item in one request) with no user required. `_get_collection()` reads the folder list (`collection.folder_names()`) before the listing, except under `--json --full` without `--folder` or once `--max-requests` is spent, then, with `--fields` and the cap not spent, the fields list (`collection.custom_fields()`; it comes after the `--folder` name is resolved, so an unknown folder fails before it is read), then lists `collection.records()` (folder 0, or the folder `--folder` names; `--sort`/`--desc` sent as `sort`/`sort_order`): server-side pages, or with `--format`/`--genre`/`--style`/`--year`/`--label`/`--artist`/`--title` a `fetch_filtered_page` scan whose `keep` is `collection.record_filter()`, each value a `collection.matcher()` pattern. `--folder` is not a filter: it is resolved by `collection.folder_id()` after the username and the folder list are read (so an unknown or ambiguous name is raised after up to 2 requests and, unlike the other argument errors, prints the budget footer), it does not make a scan (`--page` works, `--after` and `--max-requests` are rejected without a filter) and the scan, when a filter is given, reads only that folder; once `--max-requests` is spent before the folder list nothing is resolved and the empty capped page's continuation repeats `--folder` and `--fields`. `--fields` is no filter either: it adds each row's notes and custom fields by name (`projections.project_record()` and `formatting.format_collection()` take the fields list and call `collection.field_values()`), and its `Next page:` / `Continue scan:` repeat it. `--genre`, `--style`, `--artist`, `--title`, `--folder` and `--fields` belong to `get collection` alone, and `_collection_error()` rejects a ref, an empty filter or folder name, `--fields` with `--json --full` (`--full` prints the records as sent, `notes` by field id) and `--max-requests` without a filter; the click parameters are `format_` and `style_` (`style` would shadow the `style` module in `_dispatch`). `--for-sale` belongs to `wantlist` alone, `--max-price` to `wantlist` and `inventory`, `--market` to `versions`, and `--currency` to those three nouns and `stats` (`NOUN_OPTIONS`), each noun with its own rules; `_wantlist_error()` rejects a ref, a `--for-sale` flag without `--for-sale`, an unknown `--currency` (any case of a `CURRENCIES` code; a plain string option, not a `click.Choice`, so a bad code is `invalid_argument` rather than a usage error), `--max-price` without `--currency` and a negative `--max-price` before any request. With `--for-sale` it is a filtered scan through `wantlist.ForSale` (`--page` rejected, continued by `--after`); a `--cached` miss on a want's stats becomes a row with its error (`error_document()` in JSON), and `_get_wantlist()` reports it so the command exits 1.
  `--wanted` on `releases` and `versions` (`NOUN_OPTIONS`) marks release rows from each row's own want count (`collection.stat_wanted()`, Discogs' `stats.user.in_wantlist`), like `--owned` there: nothing more is sent, there is no `wantlist` object, `require_user("--wanted")` runs before any request, and `_flag_error()` rejects it on `get inventory` with a message pointing at `--in-wantlist`.
  `get collection --value` (`_get_collection_value()`) prints `collection.valuation()` instead of the listing: `{"currency", "minimum", "median", "maximum"}` with the amounts parsed, or under `--full` the currency and the SDK record unparsed (`{"currency", "value"}`), so an unknown amount format can still be seen. `_collection_error()` rejects any other `get collection` flag with `--value`, before any request.
  `get collection --count-by KEY` (`_get_collection_counts()`, a `collection.COUNT_KEYS` `click.Choice`) prints `collection.count_records()` instead of the listing: it reads the username, the folder list only with `--folder` (`_collection_folder()`, shared with `_get_collection()`), then the whole folder through `collection.read_whole()` (keep-everything, so `--max-requests` and a 429 after the first page stop it with the counts of the records read; a cap spent before the read is `collection.unread()`), and applies the filters (`record_filter()`) to the records read. `--top N` cuts the printed counts, not `distinct`. JSON is `{"count_by", "records", "without_value", "distinct", "counts", "collection"}`, `collection` being `Ownership.document()`. `_collection_error()` rejects, before any request, `--top` without `--count-by` or below 1, and with `--count-by` any of `--limit`, `--page`, `--after`, `--sort`, `--desc` (`_PAGE_FLAGS`), `--fields` and `--full`; `--max-requests` is accepted with `--count-by` alone.
  `get inventory` (`inventory`, the one noun in `USERNAME_NOUNS`) takes one Discogs username, the seller's, in place of a ref, so it needs no user: `_get_inventory()` reads `client.users.get(username).inventory` (`--sort`/`--desc` sent as `sort`/`sort_order`), as server-side pages, or with `--condition`, `--sleeve`, `--ships-from`, `--max-price` (with `--currency`, matched client-side against each listing's price currency and never sent to Discogs, unlike `get wantlist --for-sale`) or `--in-wantlist` as a `fetch_filtered_page` scan whose `keep` is `inventory.Filter`. `--in-wantlist` calls `require_user("--in-wantlist")` like `--owned` and reads the whole wantlist first (`inventory.read_wantlist()`, so `--max-requests` and a 429 stop it); when that read stops short nothing is scanned and `pagination.unscanned()` returns the empty capped page. `--owned` marks rows by the listing's release id (`inventory.release_id`), never the listing's own id. `_inventory_error()` rejects before any request anything but one non-blank username, a `--condition`/`--sleeve` that is no grade, a blank `--ships-from`, and a price filter that is not an amount in a named currency (`--max-price` and `--currency` need each other here); `--max-requests` needs a filter or `--owned`. A username starting with `-` goes after `--` in the printed continuation.
  `get stats` (`_get_stats()`, release refs and raw ids, no user) reads `releases.get(id)` first (reading `title`, so a missing release costs one request) and then its lazy `marketplace_stats.get(curr_abbr=...)`, `--currency` (`NOUN_OPTIONS`, checked by `_price_error()` in `_flag_error()`) going on the stats request only: 2 requests per ref. `wantlist.market_of()` turns the stats into a `Market`, `formatting.format_stats()` prints the one row (`_release_row()`, then `community_rating()` and the market tail) and `projections.project_stats()` the JSON, whose `market` object is `project_market()`, the one `get wantlist --for-sale` rows carry. `--json --full` is `{"release", "marketplace_stats"}`, both through `full_dump()`. A failure on either request fails the ref, never printing half its numbers.
  `get versions --market` (`market`, with `currency`, in `NOUN_OPTIONS["versions"]`; `_flag_error()` rejects `--currency` without `--market` and lets `--max-requests` through with it) reads the page as without it, the text header first as for a scan, then `wantlist.read_markets()` looks up each row's stats. `_get_versions()` returns `(output, missed)`, like `_get_wantlist()`: `_run_one()` returns that pair for every noun, and a row's `--cached` miss makes the command exit 1 without failing the ref. `_mark_markets()` writes each JSON row's `market` (`project_market()`, `null` when not checked, `error` for a miss) and the document's `market_read`; `format_master_versions()` takes the `MarketRead` and the miss messages for the row tails and the `Market:` note.
- `commands/status.py` — Show version, the SDK's `auth_mode` (from `client.auth_mode()`), and the cache location. Never calls `get_client()`, so it never opens or creates the cache.
- `commands/cache.py` — Cache management (`clear`, the only action, so the handler takes no `action` value). `clear_cache()` is inside the command's error boundary: success prints `Cache cleared.` (`{"cleared": true}` under `--json`) only when it returns; a purge or open failure (`CacheError`) exits 1 with `cache_error`, in text or the JSON envelope. The CLI deletes no database and attaches no logging handler.
- `commands/skills.py` — Serves the bundled agent guides (`skills` / `skills list`, `skills get <name> [--full]`, `skills path [name]`). Every directory of `src/agent_discogs/skills/` holding a `SKILL.md` is a skill (`core`, `collection`, `marketplace`, `pressings`), with optional `references/*.md` that `--full` appends; all of it ships in the wheel. `skills list` pads the names to the longest; `skills list --json` prints `[{"name", "description", "version"}]` through `json_output.dump()`, its `--json` uncolored by `off_for_json` like every other. `skills/agent-discogs/SKILL.md` at the repo root is a thin discovery stub that points agents at `agent-discogs skills get core`, then the skill the task needs, and tells them never to guess commands or flags and what to do when the installed binary lacks a skill it names; do not put feature content there.
- `commands/completion.py` — `completion bash|zsh|fish` prints click's own completion script (`BashComplete`/`ZshComplete`/`FishComplete.source()`) for the root command, under the fixed program name `agent-discogs` and its `_AGENT_DISCOGS_COMPLETE` variable; no hand-written scripts. Like `status`, it never calls `get_client()`. What Tab offers comes from the commands themselves: `click.Choice` types, plus `shell_complete` callbacks for the `search` type word (first positional only), `get --sort` (the noun's keys: after `--sort ` click stops parsing at the option awaiting its value, so the noun is left in `ctx.args`; after `--sort=`, one word in zsh and fish, it is in `ctx.params`), `get --currency` (the codes, uppercase, matched in any case) and skill names. Aliases are resolved by `AliasGroup.get_command` but never listed, so they are not offered.

### Core Modules

- `config.py` — Leaf module (imports nothing from the package) holding shared configuration: `cache_dir()` and `CACHE_TTL` (and `CACHE_TTL_LABEL`, the `1h` that `status` and the `--debug` panel print). `cache_dir()` is `$XDG_CACHE_HOME/agent-discogs` when that is non-empty and absolute, else `~/.cache/agent-discogs`; it resolves on each call and looks up home only on the fallback, so nothing touches home at import. Put new shared constants here rather than in a module that needs them, so the package stays free of import cycles.
- `client.py` — Singleton `Discogs` client. Passes no credentials: the SDK resolves them from the `DISCOGS_*` environment variables (token, then OAuth, then consumer key/secret), so never check one variable yourself; `auth_mode()` reads the selected mode from a throwaway client built without a cache. Cache settings come from `config.py`. Built with `max_retries=0`: the CLI never retries or sleeps on the caller's behalf, so each request that reaches the network is sent once. `get_client()` also enters the cache scope the global flags requested. Neither step does I/O: the SDK opens its SQLite cache at the first request that needs it, so an unusable cache raises `CacheError` inside the command's error boundary (a `cache_error` envelope under `--json`), and a `no_cache()` (`--fresh`) command never opens it. Nothing in the CLI deletes a cache database.
- `refs.py` — Typed ref system (`@a3857`, `@r847868`, `@m3719`, `@l647`). `make_ref()` creates refs, `parse_ref()` parses them. Raw numeric IDs return type `"unknown"`.
- `pagination.py` — Reads exactly one page with full metadata (`total_items`, `total_pages`) through the SDK's public `SyncPage.fetch()`, where iterating a `SyncPage` would fetch the next page as soon as the current one runs out. Callers pass a `Listing`: the SDK's paginated resource method with its filters bound (`functools.partial(client.search, **params)`, `label.releases.list`), which `fetch_page` calls with `page`/`per_page`. The SDK owns endpoint paths, item keys, models, and the envelope checks; a malformed page raises `DiscogsError`, and a page that fails to parse is never cached. Never reach into SDK internals here. `fetch_filtered_page(..., keep_sends=True)` is for a `keep` predicate that itself sends a request (the wantlist's per-want stats lookup): the cap is then checked before each row, and a 429 from `keep` stops the scan on any page; see Client-Side Filtering. `keep_all()` is the `keep` of a scan that reads a whole listing (`limit=None`), as `inventory.read_wantlist()` does; `unscanned(cursor, stop)` is the empty capped `PageResult` (no totals, continuing from the cursor it was asked for) of a filtered scan that never started because a read its filter needs first stopped short.
- `account.py` — The Discogs user behind the credentials. `require_user(feature)` raises `UserRequiredError` before any request unless `client.auth_mode()` is `token` or `oauth` (`errors.classify()` maps it to `auth_required`, no `status`); `username(client)` is `GET /oauth/identity`, looked up once per invocation (kept in `ctx.meta`, so `--fresh` does not repeat it); `user(client)` is the SDK's handle on that user (`client.users.get(username)`), for their collection, lists and wantlist. Every command that reads the user's own data goes through here.
  `currency(user)` reads `curr_abbr` from the profile (the proxy's `currency_code`, one request) and `amount(text, field)` reads a number out of a formatted amount (`"€1.250,00"`: the symbol before the first digit and after the last is dropped, unless it holds a sign or parentheses or ends in `.`/`,` right before the first digit; the last `.`/`,` followed by one or two digits is the decimal point; other `.`, `,`, `'`/`’` and spaces, no-break and narrow no-break included, separate thousands in groups of three after a first group not starting with 0; the result must be finite). Both raise `UnknownFormatError(field, problem)` on anything else; it is not a `ValueError`, so `errors.classify()` maps it to `bad_response` (with a report-it hint, which points at `--json --full` for an amount, not for `CURRENCY_FIELD`) instead of `invalid_argument`, and its message names the field, never the value.
- `collection.py` — The authenticated user's collection. `records(user, folder=, sort=, desc=)` is the one listing of a folder's records, by default the "All" folder (`ALL_FOLDER`, folder 0): `get collection` without `--folder` and the `--owned` read both use it, so without `--sort` they send the same requests and share cache entries. `folder_id(names, name)` resolves a `--folder` name against the folder list (`folder_names()`), any case, and raises `ValueError` naming the folders for no match or for two folders with the same name. `matcher(pattern)` is the one matching rule of every `get collection` filter: the whole value, casefolded, with `*` for any run of characters and `\` to make the next character literal (`\*`, `\\`; a trailing lone `\` is a backslash); `?`, `[` and regular-expression characters are literal, so `fnmatch` is not used. `record_filter(filters)` is the `get collection` `keep` predicate (None without a filter): a record is kept when, for every filter (`format`, `genre`, `style`, `year`, `label`, `artist`, `title`), one of its values (format names and descriptions, genres, styles, label names, the year as decimal text, credited artist names, the release title) matches the pattern (`matcher()`). `user_stat(row, name)` reads the authenticated user's own `stats.user.<name>` (`in_collection`, `in_wantlist`) off a `get versions` or `get releases` row, a modeled `VersionStats` or the plain dict an artist or label row keeps, with its own attribute/key lookup (it cannot import `formatting.field()`: `formatting` imports `collection`), and `None` for anything that is not an integer; `stat_copies(row)` is its `in_collection`, the count `--owned` marks those rows with, `stat_wanted(row)` whether its `in_wantlist` is 1 or more (`--wanted`), and `mark_rows_with(document, items, key, value)` writes one key on each JSON release row. `ownership_of()` (`search` and `get inventory`, whose rows carry no reliable count) returns `None` without a request when a page holds no release row, else reads the "All" folder once per invocation (100 records a request, through `fetch_filtered_page` with a keep-everything predicate, so `--max-requests` and a 429 stop it like any scan) into an `Ownership`: copies per release id, records read, total, and the `ScanStop`, if any. `Ownership.owned(release_id)` is `0` only after a complete read, else `None` (undecided) unless the part read holds the release (and `None` for no release id); `mark_rows(..., release_id=)` writes `owned` on JSON rows and the `collection` document, looking each row up by the id `release_id` gives: by default the row's own `id`, and `get inventory` passes `inventory.release_id`, since a listing's own id is not its release's. `inventory.is_release_row()` decides which rows are marked (rows with a `type` other than `release` are not). `folder_names(user)` is the folder list, read at most once per invocation (`ctx.meta`), and `folder_name()` names one copy's folder (`folder 123` for an id the list lacks). `custom_fields(user)` is its twin for `get collection --fields`: the user's notes and custom fields by id (`CustomField`: name and whether it is a dropdown), one request, read at most once per invocation (`ctx.meta`), in the order of the fields' `position` (then id), a name two fields share becoming `Name (field N)`; `field_values(record, fields)` turns a record's `notes` into the row's `name: value` pairs in that order, a grade in a dropdown field as its short code (`inventory.short_grade()`), anything else as sent, empty values and notes without a `field_id` dropped, and a `field_id` the list lacks as `field N` after the rest. `copies()` serves `get owned`: the username, one request for the release's instances, and the folder list (once, only when owned and not `--full`).
  `Ownership.records` keeps the records read, in collection order, for `master_copies(client, master_id, folders=)`, which serves `get owned @m...`: the same collection read as `ownership_of()` (the `ctx.meta` entry they share, once per invocation, uncapped and never skipped, since `get owned` takes no `--max-requests`), filtered on `basic_information.master_id` (0 or None matches nothing), into a `MasterCopies`: the matching records, `(release id, copies, folder names)` per release in the order of its first copy, and the `Ownership`. Its `owned` is the copies found, `0` only after a complete read, else `None` when none were found. The folder list is read only with `folders` and a copy found, and a 429 on it leaves the folders named by id (`folder 5`) rather than failing the ref; the empty name map is then stored as the invocation's folder list, so no later ref asks again. A `RateLimitError` in the read is a stop (the part read answers); any other error, `CacheMissError` included, propagates, and the next master ref tries the read again.
  `valuation(client)` serves `get collection --value`: the username, the profile's currency (`account.currency()`), and the lazy `collection.value.get()` record; `Valuation.amounts()` parses its three strings with `account.amount()`.
  `count_records(records, key)` serves `get collection --count-by`: a `Counts` (records counted, records with no value, `Group(value, ref, count)` per value, largest first, ties by casefolded value). A record counts once per distinct value (`_count_values()`): labels and artists by id (with their ref; by casefolded name when Discogs sent no id), the year as text, the decade as `1990s`, format names, genres and styles casefolded; a value is spelled as in the first record that has it. `read_whole(listing, max_requests=)` is the one keep-everything read of a folder into an `Ownership` (the `--owned` read and `--count-by` use it), and `unread(stop)` the `Ownership` of a read that never started.
- `wantlist.py` — The `get wantlist --for-sale` filter. `ForSale` is the `keep` predicate of the scan: one `releases.get(id).marketplace_stats.get(curr_abbr=...)` per want (a lazy proxy, so reading `num_for_sale` sends the one request), cached like any request. It keeps a want with copies for sale that is not `blocked_from_sale` and, with `max_price`, whose lowest price is known and at most that (exactly at it is kept), storing each kept want's `Market(for_sale, lowest)` in `markets`. A `CacheMissError` keeps the want too, as undecided, with its error in `misses`: a want whose stats were not read is never reported as not for sale. Any other failure propagates, and a `RateLimitError` stops the scan (`fetch_filtered_page` with `keep_sends=True`). The Discogs API has no endpoint listing a release's copies for sale, only these stats, so condition, sleeve condition, seller location and shipping cannot be filtered; do not add flags for them.
  `Market(for_sale, lowest)` is a release's Marketplace numbers wherever they are shown: `market_of(stats)` builds it from a stats record for `get stats`, a `null` count read as 0 and a release blocked from sale as `Market(0, None)` (the caller checks `blocked_from_sale` to add `"blocked": true`).
  `read_markets(client, rows, currency=, max_requests=, listing_stop=)` serves `get versions --market`: one stats lookup per row in order, sent only while `trace.sends()` is below the cap (the listing's sends count first, cache hits are free), a 429 stopping the lookups with the rows read and a `CacheMissError` recorded per row; any other failure propagates. After a listing scan stopped by a 429 (`listing_stop`) it sends nothing and returns an `unsent` read carrying that stop, like `inventory.wants_of()` after an earlier 429. It returns a `MarketRead`: markets by release id, the ids blocked from sale, the misses, the row count and the `ScanStop`, if any; `MarketRead.document()` is the JSON `market_read` object, and `rows_read` counts a miss as read.
- `inventory.py` — The Discogs grades and the `get inventory` filters. `GRADES` is the one grade ranking (the name Discogs sends → its short code, best first: M, NM, VG+, VG, G+, G, F, P). It is ours and depends on no order of discogs-sdk's `Condition` literal, which is no documented contract, and it replaced the price guide's own condition list (`format_price_guide()` iterates it). `grade(text)` resolves a short code or a full name, any case, to the Discogs name (None for anything else); `short_grade(name)` gives the code (`VG+`), and a value that is no grade (a sleeve `Generic`, `Not Graded` or `No Cover`) as sent. `release_id(listing)` is the id of the release a listing is a copy of, which `--owned` and `--in-wantlist` look up. `is_release_row(row)` is whether a list row is a release, the only thing a collection or a wantlist holds (a row with a `type` other than `release` is not); it lives here, not in `collection`, because `collection` imports this module (`short_grade`) and `wants_of()` needs it. `read_wantlist(client, max_requests=)` reads the user's whole wantlist (the username, then 100 wants a request, through `fetch_filtered_page` with `keep_all`) into `Wants`: the wanted release ids, wants read, total and the `ScanStop` if any; `Wants.document()` is the JSON `wantlist` object, and `Wants.wanted(release_id)` is `True` when the part read holds it, `False` only after a complete read, else `None`. `wants_of(client, listing, earlier=, max_requests=)` serves `search --wanted`: `None` without a request when the page holds no release row, an unread `Wants` (no request) when one of the `earlier` stops (the listing's, the `--owned` read's) is a 429 or the cap is already spent, so not even the username is asked, else `read_wantlist()`. `Filter` is the `keep` predicate of the scan and sends nothing: minimum media and sleeve grades (a sleeve that is no grade fails any `--sleeve`), an exact casefolded ships-from country, a price cap `(amount, currency)` matched against the listing's price currency (an other-currency listing is dropped and counted in `skipped_currency`, one with no price dropped uncounted) and the wanted release ids.
- `formatting.py` — All output formatting. Returns plain strings, callers `print()` them. Every view returns `_text(lines)`, which runs each line through `sanitize.line()`; build new views the same way so a Discogs field can never add a line or print a raw control character. A line is a string, or a list of parts (`markup.Part`): text, which may hold Discogs values, `style.Span`s for the CLI's own framing (`_ref()`, `_label()`, dimmed counts and footer prefixes), and `style.Styled` runs of Discogs text under the attributes its markup asked for. With color off the parts are joined and neutralized as one string, so the output is exactly the plain text; with color on each text run is neutralized and each span or styled run painted around its neutralized text. Never put a Discogs value in a `Span`, and never build a `Styled` outside `markup`.
- `markup.py` — Converts the Discogs markup in artist and label profiles and release notes, for the text views and the `--json` projections alike (`--full` keeps it raw): `parse()` turns `[a123]`/`[l123]`/`[r123]`/`[m123]` and `[r=123]`/`[m=123]` into ref `Span`s, `[a=Name]`/`[l=Name]` into the name, `[url=…]text[/url]` into `text (host)` and `[url]…[/url]` into `host`, `[g1.2]`/`[t=1]` into the text Discogs shows, and `[b]`/`[i]`/`[u]`/`[s]` into `Styled` runs; anything else, uppercase tags included, stays as written. One linear pass (`_Parser`) styles each run of text under the tags open when it arrives: an unclosed tag ends with its field, a stray closing tag is dropped, a link inside a link stays text, and the result is trimmed. `profile()` also truncates (`truncate()`: converted characters, never inside a ref) and `split_lines()` cuts parts at line breaks with their styles. It writes no escape code: conversion runs before `sanitize.line()`, painting after.
- `sanitize.py` — Neutralizes untrusted text for the text views: `line()` turns line breaks and tabs into spaces and other control/bidi characters into visible escapes; `summary()` also collapses whitespace and bounds the length (API and connection error details, in text and JSON alike). Discogs data values in `--json` output never go through it.
- `style.py` — Terminal color, for a person at a terminal and never an agent. `enabled(stream)` answers whether that stream gets color: `--color always`/`never` decide, and `auto` (the default) colors only a terminal (`isatty()`), with `NO_COLOR` unset or empty and `TERM` not `dumb`; outside a command it is off. The mode lives in `ctx.meta` (`configure()`), so it is fresh per invocation; every `--json` flag has the `off_for_json` callback, which turns color off for the whole command, stderr included. `paint(text, *styles, color=...)` wraps already-neutralized text in the SGR codes of its styles, then a reset, when `color` is true; `_SGR` is the one palette. A `Style` is framing (a `Span`) and may be a color; an `Attr` (bold, italic, underline, strike) is the only styling Discogs text gets (a `Styled` run), never a color. Callers decide per stream: text views on stdout (`_text`), `format_error(color=...)` on stderr (or stdout for a multi-ref block), and the footer and `--debug` panel on stderr. `--help` and `skills` never paint.
- `errors.py` — `classify()` maps SDK exceptions to an `ErrorInfo` (stable `code`, message, hint, `retry_after`, `status`, `limit`/`remaining` on 429, and `path` on `cache_error`); `format_error()` renders text (neutralized), `format_error_json()` the `{"error": {...}}` envelope; `fail()` prints one or the other and exits 1. A 404's hint suggests a search, except for a list (context `List <id>`), which search cannot find: `_LIST_NOT_FOUND` points at `get lists`. The 401 (`auth_required`) and 429 (`rate_limited`) advice follows `client.auth_mode()`, the mode `status` reports: a 401 names the credentials that were sent (`_REJECTED`) and points at `agent-discogs status`; a 429 tells only an unauthenticated caller to set `DISCOGS_TOKEN`, and otherwise states the limit Discogs reported (the authenticated 60/min when the 429 carried no rate-limit headers). An API error's body text (`_api_message()`, the SDK message) enters a message only through `sanitize.summary()`, after the status; so does a `DiscogsConnectionError`'s cause, whose hint follows the SDK's `transient` flag (retry, or fix the configuration) so `src/` never imports `httpx2`. The `CacheMissError` branch only builds the error: the footer learns about the miss from the SDK's own `source == "miss"` event. `CacheError` becomes `cache_error`: the message names the database path, the failed operation and the cause's class; the hint points at permissions/ownership or deleting the file by hand. `unexpected` messages name the exception class (`_describe()`, with the module outside builtins). A 2xx the SDK cannot read (`JSONDecodeError`, `UnicodeDecodeError`, pydantic `ValidationError`, or a bare `DiscogsError` from its envelope checks) is `bad_response`, checked before the `ValueError` → `invalid_argument` branch since all but the last are `ValueError`s; a validation error is described by its first failing field, never the value. agent-discogs has no envelope or schema checks of its own.
- `trace.py` — Per-invocation request trace. `record()` is the client's `on_request` hook and keeps every event: cache hits, network responses, transport failures (`status_code` None) and `cache_only()` misses (`source == "miss"`). The footer's count is the `attempts` of the network events, so a failed send counts and a miss costs nothing; its low-budget hint suggests a token only when the last reported `RequestEvent.ratelimit.limit` is below the authenticated 60/min, never from which variables are set. The `--debug` panel has a row only for events with a status code. `begin()` (group callback) resets state and registers `finish()` via `ctx.call_on_close`, which runs on every exit including `sys.exit(1)`. `finish()` prints the budget footer (`api: N requests · R/L left this minute`) and, under `--debug`, the panel — both to stderr, never stdout. `fetch_filtered_page` reports a `ScanNote` per scan.
- `json_output.py` — `--json` emission. `Mode(json, full)` tells a handler how to emit; `Mode.entity()` and `Mode.page()`/`page_document()` take a projector and bypass it under `--full`; `dump()` prints the finished document. Build documents inside a command's error boundary and print outside it. `dumps()` is the one serializer, shared with the error envelope: non-ASCII is literal only when stdout is UTF-8, and `_ALWAYS_ESCAPED` (C1, bidi, U+2028/9, lone surrogates) is always `\uXXXX`. Never call `json.dumps` for output directly. `full_dump()` is every `--full` path's serializer for an SDK model: `model_dump(mode="json")`, the SDK's normalized record (its field names, RFC 3339 timestamps, `null` for an unparseable one, unmodeled fields as sent). Never print `model.raw` or a Python-mode `model_dump()`.
- `projections.py` — One projector per text view (`project_release`, `project_search_result`, ...) returning exactly the fields the text shows, plus refs and `url` (`_url()`: the entity's or row's `uri`, or a list's own `url`, a site-relative one completed to `https://www.discogs.com`; JSON-only, never in text). Every projector of something Discogs may give a page carries it: release, master, artist, label, search result, list, `get lists` row, and the `versions`/`releases` rows (which carry no `uri` today); the release facets (tracklist, price, credits, identifiers) and list items do not. Empty values are dropped. Two exceptions to "exactly the fields the text shows": a timestamp the text prints as a day (`get collection` `added`, `get lists` `changed`) is the full RFC 3339 timestamp in JSON, and `project_record()` (the `get collection` row) also carries release data the text row does not show, read from the same response: `artists` (`[{"ref","name"}]`, no `join`), `genres`, `styles` and `master` (none for Discogs' `0`). This is what `--json` prints; `full_dump()` is `--json --full` only.

### Client-Side Filtering

`fetch_filtered_page()` in `pagination.py` handles filters the Discogs API doesn't support server-side (e.g., release type in search, credit role in artist releases). It reads 100-row API pages, applies a `keep` predicate client-side, and keeps going until the user's page is full or the listing ends: there is no default cap. `--max-requests N` (`max_requests`) caps the HTTP sends of the whole command, counted by `trace.sends()` from the request events, so header lookups count and cache hits are free; text-mode header lookups (`artist.name`, `label.name`) therefore run before the scan. A `RateLimitError` after the first page returns the rows read so far. Either early stop sets `PageResult.stop` (a `ScanStop`), which `page_document()` reports as `capped`/`stop_reason`/`retry_after`; a scan that read no page has `None` totals (JSON `null`). `--max-requests` is validated (≥ 1, scanning listing, one ref) before any request.

A continuation cursor is `<display_page>:<row>`, `row` being the absolute 0-based position of the first raw row not scanned yet, so it does not depend on the scan's page size; `parse_cursor()` rejects the older `<page>:<api_page>.<offset>` form rather than read it at another size. Under `--fresh`, text `get releases` and text `get versions --release-type` scans (`official`, or `unofficial` with `--format`) send their header on every run, so when the header spends the whole budget the empty capped page's header (`header_resent`) says to continue with a higher `--max-requests`.

`keep_sends=True` serves `get wantlist --for-sale`, whose `keep` sends a request per want: the cap is checked before each row too, so it can stop mid-page, and a wants page is asked for only while at least 2 sends remain after the sends so far (the page plus one want's stats), so the cap never spends its last send on a page none of whose wants can be checked (`--max-requests` below 3 is rejected with `--for-sale`: the username, a wants page and one want's stats, all sent on a cold cache or under `--fresh`, so even then one want is checked per run; at a page boundary the scan stops with the boundary cursor). A 429 from `keep` keeps the rows kept so far on any page (a 429 on the first wants page still propagates). The cursor then names the first row `keep` did not decide, so a continuation checks it first and never checks a row twice.

### Ref System

Refs are stateless: `@r847868` is just the Discogs ID with a type prefix, so nothing is stored between invocations and refs never expire. Smart resolution: `get versions @r123` auto-resolves a release ref to its `master_id`.

- Runtime: `click`, `discogs-sdk`, `pydantic`
- Dev: deptry, pre-commit, pyproject-fmt, pyright, ruff, ty, plus the `test`
  group. The `pre-commit` recipes run it through `uv run`, so no global
  install is needed.
- Test group: pytest, pytest-cov. Kept separate because CI installs it on its
  own (`uv export --only-group test`) into the clean environment where the
  built wheel is tested; anything added here lands in that environment too.
- KLUDGE: `deadcode` is deliberately *not* a dev dependency. It crashes on
  Python 3.14 (it calls `ast.Str`, which 3.14 removed) and upstream is
  dormant, so `just dead-code` runs it through `uvx` pinned to Python 3.13.
  The justfile recipe, the CI step, and the pre-commit hook each carry
  `KLUDGE` comments with the details — grep for `KLUDGE` before changing the
  dead-code check, and do not "simplify" its exit-code handling.
- Python 3.15 is supported. discogs-sdk (0.7.0 and later) declares
  `pydantic>=2.14; python_full_version == '3.15.*'`, because pydantic 2.13
  pins a pydantic-core with no cp315 wheels and 2.14 is the first series with
  them. Every resolved pydantic is a stable release, and
  `scripts/check_installed_package.py` asserts the 2.14 minimum on 3.15 with
  no upper bound. Consequences to keep in mind:
  - The committed lockfile may carry a 3.15-only pydantic branch (2.14.x on
    3.15, an older locked pydantic elsewhere). It exists only while the other
    Pythons' resolution lags 2.14, and collapses on the next full upgrade
    (`just deps-update`). Either shape is correct.
  - Do not exclude 3.15 with `[tool.uv] environments`: that makes the `3.15`
    CI leg unresolvable.
  - Our own `pydantic>=2.12.5` floor stays as is; the SDK's marker-scoped
    clause raises it on 3.15.
  - Exercise 3.15 locally with
    `UV_PROJECT_ENVIRONMENT=.venv315 uv sync --all-extras --all-groups \
    --python 3.15 --locked`, then `UV_PROJECT_ENVIRONMENT=.venv315 uv run \
    --python 3.15 --locked pytest`.
  - If a 3.15 marker of our own ever becomes necessary, copy the SDK's
    equality-star form (`python_version == '3.15'`, published as
    `python_full_version == '3.15.*'`), which matches release candidates.
    `python_version >= '3.15'` does not: uv-build rewrites it — and every
    pre-release boundary such as `3.15.0.dev0` or `3.15.0rc1` — to
    `python_full_version >= '3.15'` in the published metadata, and under
    PEP 440 a release candidate sorts *below* 3.15.0, so the marker is false
    on exactly the interpreters that need it and pip fails to resolve at all.

## Key Conventions

- Python 3.10+ required
- `py.typed` marker present (PEP 561)
- Imports live at module scope; ruff's `PLC0415` enforces it. Only `TYPE_CHECKING` blocks may import inside a function or block.
- Run `git` commands directly, never with `git -C`
- Never commit on `main`. Work starts on a branch named `<type>/issue-<N>-<slug>` for an issue, otherwise `<type>/<slug>`, where `<type>` is the Conventional Commits type of the change (`feat`, `fix`, `docs`, `test`, `ci`, ...). The one exception is a version change, which goes on `release/v<version>`, created by the [release recipes](#releasing). Either way it lands through a pull request.
- Pull requests land by squash merge (the only method the repository allows): `gh pr merge <n> --squash`, or, for a stack, `gh stack merge --yes --squash` run with no number from a worktree that has the stack checked out (a bare number is read as a stack number before a pull request number). GitHub signs the squash commit itself, but `main`'s signed-commit ruleset also checks every commit on the pull request branch, so each one must be signed and verified: an unsigned commit blocks the merge until it is rebased, signed, and force-pushed. The pull request title becomes the commit subject, and git-cliff builds the changelog from it, so write the title as a Conventional Commit (`fix: ...`, `feat(cache): ...`).
- When adding or changing user-facing behavior (commands, flags, output shape, errors), update all of: `_HELP_TEXT` in `src/agent_discogs/__init__.py`, the matching `docs/` page (`commands.md`, `json-output.md`, `caching-and-budget.md`, `errors.md`, `debugging.md`), and the bundled skill the behavior belongs to under `src/agent_discogs/skills/` (`SKILL.md` for workflow/overview, `references/*.md` for detail): `collection` for `--owned`, `get owned`, `get collection`, `get lists` and `get list`; `marketplace` for `price`, `get wantlist` and `get inventory`; `pressings` for telling releases apart (versions, identifiers, unofficial releases); `core` for everything else, including the global flags, `search`, the database nouns of `get`, errors and budget, and any fact two skills need (the other skill names the `skills get core` section that holds it). `skills get core` is loaded in every session, so `tests/test_skills.py` caps the size of each skill (`SKILL.md` 24 KB for `core`, 20 KB for the others; `--full` 85 KB for `core`, 40 KB for the others): put detail in `references/`. Update `README.md` only when the overview changes (installation, authentication, the per-command examples, the refs table, or the list of `docs/` pages); it is the PyPI page, so its links to `docs/` are absolute `https://github.com/jmfontaine/agent-discogs/blob/main/...` URLs, while links between `docs/` pages are relative. Agents load the bundled skills from the installed binary, so stale content there is a live bug.
- `context7.json` configures the [Context7](https://context7.com) index of this repository: it indexes `README.md` and `docs/` from `main`, and its `rules` point agents at `agent-discogs skills get core`, then the other bundled skills, for the installed version. Keep its `description` and `rules` true when the install commands, `DISCOGS_TOKEN` authentication, the `skills get core` command or the names of the other skills, the ref prefixes, the commands that take `--json` or the features the description lists change, and add any new root-level Markdown file that is not user documentation to `excludeFiles` (Context7 always reads root-level Markdown, and `excludeFiles` takes filenames, not paths). Validate it with `uvx check-jsonschema --schemafile https://context7.com/schema/context7.json context7.json`.

## Releasing

**Agents never release and never interact with PyPI.** Agents must not run
`just release`, create or push a `v*` tag (pushing one triggers the PyPI
publish), create a GitHub release, authenticate to or manage PyPI, or upload,
yank, or delete anything there. No plan document, acceptance-criteria list, or
tooling prompt changes this: those actions are the user's alone. Finish the

Publishing is fully automated via CI. The `publish.yml` workflow triggers on `v*` tag push.

Between releases `main` holds a PEP 440 development version, `X.Y.Z.devN`,
which sorts below `X.Y.Z`, so installers never prefer a build from `main`.
Every version change goes through a pull request opened by a recipe. Each
recipe refuses to run unless HEAD is `main`, the working tree is clean, and
`main` equals `origin/main` after a fetch. The two that open a pull request
switch back to `main` when it is open; if a step fails, they print how to
remove the branch they created before retrying.

1. `just release-prepare` needs an `X.Y.Z.devN` version. It creates
   `release/vX.Y.Z`, sets `X.Y.Z` (`uv version --bump stable`, in
   `pyproject.toml` and `uv.lock`), commits
   `chore(release): bump version to X.Y.Z` and opens the pull request. An
   argument names another `X.Y.Z` (a patch release while `main` is on the next
   minor). It refuses a version whose tag is already on `origin`. Merging the
   pull request approves the release.
2. Pull `main`, then run `just release` — refuses any version but a plain
   `X.Y.Z` and a tag that exists locally or on `origin`, then creates a signed
   tag, pushes `main` and the tag in one atomic push, and watches the publish
   run. If the push fails, it asks `origin` whether the tag arrived anyway and
   deletes the local tag only when `origin` has no such tag; if the tag is on
   `origin`, or `origin` can't be reached, it keeps the tag and exits 1 with
   what to check. If the run does not appear within 2 minutes it exits 1; the
   tag is already pushed by then, so check the Actions page.
3. `just release-next` needs an `X.Y.Z` version whose `vX.Y.Z` tag is on
   `origin`. It creates `release/vX.(Y+1).0.dev0`, sets that version, commits
   `chore(release): start X.(Y+1).0 development` and opens the pull request.
   `just release-next patch` opens `X.Y.(Z+1).dev0` instead, and
   `just release-next major` `(X+1).0.0.dev0`. Merge it to reopen development.

`publish.yml` calls the reusable `checks.yml`, which builds the distributions
once, checks them with `scripts/check_distributions.py` (archive contents:
`py.typed`, `LICENSE.txt`, the bundled skill, no project-only trees) and
`twine check --strict` (metadata), then installs the built wheel into a clean
environment on the oldest and newest supported Python, runs
`scripts/check_installed_package.py` (import path, pydantic branch, console
script offline) and the whole test suite against it, and installs the sdist on
the newest. Every push and PR runs the same jobs. The publish job downloads
those exact artifacts and never rebuilds, so what PyPI receives is what was
tested. Publishing uses PyPI Trusted Publishers (OIDC); the `pypi` GitHub
environment must exist on the repo.

A release cannot be replaced once uploaded. If a broken version reaches PyPI,
yank it there (project page or the upload API — there is no `pip yank`), then
release the next patch version with `just release-prepare X.Y.(Z+1)` (run
`just release-next` first if `main` still holds `X.Y.Z`).
